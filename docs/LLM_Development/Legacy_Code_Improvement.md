# LLM을 활용한 레거시 코드 개선과 검증 기록

작성일: 2026-09-07. LLM을 코드 이해·개선안 탐색에 활용하되, 변경의 정확성과 운영 적용 판단을 개발자가 검증하는 작업 가이드다.

## 현재 기록된 적용 경험

- 반도체 수율 개선을 지원하는 수학적 로직의 계산 복잡도를 낮추는 데 LLM 활용
- 시간 동기화와 관련된 기존 로직의 오류 수정
- 프로젝트의 구현 방식과 코딩 스타일 일관성 개선

구체적인 알고리즘 전후 Big-O, 측정 시간, 실제 수율 변화, 시간 오류의 세부 원인은 아직 이 기록에 포함하지 않았다. 아래는 해당 경험을 보완하거나 **다음 변경에서 사용할 검증 절차**이며, 모든 절차를 이미 수행했다는 뜻은 아니다.

## 1. 알고리즘 변경: 정답과 비용을 각각 검증

먼저 입력 크기 `n`의 의미와 보존해야 할 조건을 정의한다. LLM에는 개선 코드뿐 아니라 복잡도 계산 근거와 결과가 달라지는 반례를 함께 요청한다.

| 확인할 것 | 검증 방법 |
| :--- | :--- |
| 업무 규칙 보존 | 작은 입력의 손계산 결과 또는 검증된 기준 구현과 비교 |
| 경계값 | 빈 입력, 하나의 원소, 중복, 최댓값·최솟값, 결측 데이터 |
| 수치 오차 | 연산 순서 변경 시 절대/상대 오차 허용 범위를 업무 기준으로 정의 |
| 복잡도 | 중첩 반복, 정렬·탐색·해시 비용, 평균/최악 조건을 구분 |
| 시간·메모리 | 입력 크기를 늘리며 동일 환경에서 시간, allocation, peak memory 비교 |

기존 구현 자체에 버그가 있다면 “기존 결과와 같음”만으로 충분하지 않다. 도메인 규칙에서 독립적인 기대값을 만든다. 속도 측정은 warm-up, 입력 분포, 동시성, 반복 횟수와 측정 환경을 함께 남긴다.

“계산 복잡도 감소”, “실행 시간 단축”, “반도체 수율 증가”는 서로 다른 결과다. 측정하지 않은 결과로 확대해서 서술하지 않는다.

## 2. 시간 관련 오류: 어떤 시간을 비교하는가

“시간 동기화”는 서버 시계 오차, timezone 변환, 이벤트 순서, timeout, 동시 접근을 가리킬 수 있다. 먼저 실제 오류가 어느 범주였는지 재현 입력과 함께 적는다.

- 이벤트가 발생한 시각과 서버가 받은 시각을 구분한다.
- 날짜 경계, timezone·offset, 초/ms 단위 변환을 확인한다.
- 중복 이벤트, 지연 도착, 역순 도착과 재시도를 포함한다.
- 업무상의 현재 시각은 `Clock`을 주입해 고정된 시점으로 테스트한다.
- 같은 JVM에서 경과 시간을 잴 때는 `System.nanoTime()`의 차이를 사용한다. 그 값을 저장해 다른 JVM의 timestamp와 비교하지 않는다.

`Clock.fixed/offset`은 테스트 시각을 제어하는 수단이며 서버 시계를 동기화하지 않는다. `nanoTime`도 UTC 시각이나 분산 이벤트의 전체 순서를 제공하지 않는다. [Clock API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/time/Clock.html), [System.nanoTime API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/System.html#nanoTime())

시간 버그 수정에는 잘못된 입력·기존 결과·기대 결과·수정 후 결과를 한 세트로 남긴다.

## 3. 프로젝트 스타일과 구조의 일관성

포맷 변경과 동작 변경을 나누어 검토하면 리뷰 범위가 작아진다. 먼저 예외 처리, 로그, 이름, 패키지 책임, 테스트 규칙 등 합의된 기준을 짧게 적는다.

1. 대표 모듈 하나에 적용해 기존 흐름과 맞는지 확인한다.
2. 포맷·import 정리는 formatter나 lint로 반복 가능하게 만든다.
3. 예외·transaction·비동기 경계 등 동작이 달라질 수 있는 변경은 별도 리뷰한다.
4. 영향을 받는 테스트를 실행하고 여러 모듈로 확장한다.
5. “규칙을 적음”, “일부 적용”, “전체 적용”, “CI에서 검사” 중 실제 완료 범위를 표시한다.

## 4. LLM에 요청할 때 남길 조건

```text
목표: [변경하려는 문제]
보존해야 할 규칙: [입력/출력, 순서, 오차, transaction, 호환성]
범위: [대상 모듈과 변경하지 않을 외부 계약]
먼저 현재 코드의 동작과 실패 가능한 입력을 설명해줘.
개선안별 복잡도, 메모리 비용, 동작이 달라지는 조건을 비교해줘.
테스트는 변경 전 실패 / 변경 후 성공 여부를 확인할 수 있게 제안해줘.
확인할 수 없는 사실과 성능 수치는 추정으로 구분해줘.
```

실행·테스트 결과가 없는 “수정 완료” 응답은 완료 근거가 아니다. 사내 코드와 데이터는 허용된 도구·환경에서 다루며 공개 TIL에는 회사 식별 정보와 실제 고객 데이터를 제외한 재현 예제를 남긴다.

```markdown
### 문제와 영향
- 입력/상황:
- 기대 동작과 실제 동작:

### 분석과 선택
- 실제 원인:
- LLM이 도운 부분:
- 개발자가 확인한 근거:
- 비교한 대안과 선택 이유:

### 변경과 검증
- 코드 변경 범위:
- 재현/회귀 테스트:
- 전후 Big-O와 n의 정의:
- 측정 조건 및 결과:
- 배포/운영 확인 범위:

### 남은 확인
- 알려진 제약:
- 아직 측정하지 않은 항목:
```

모델 사용 자체보다 어떤 가설을 검증했고 어떤 변경을 책임졌는지가 핵심 기록이다.
