# TIL 트러블슈팅 기록

관측된 사실과 아직 확인하지 못한 설명을 구분해, 다른 사람이 재현·진단할 수 있게 기록한다. 경로는 저장소 루트 기준이다.

작성 전에 [til-natural-writing](../til-natural-writing/SKILL.md)을 함께 적용한다. 증상과 원인을 자연스럽게 연결하고, 템플릿의 모든 항목을 채우기 위한 문장이나 작성일·확인일은 덧붙이지 않는다.

## 자료와 기존 기록 확인

1. 오류 문구·제품명·핵심 API로 `docs/`를 검색해 같은 문제의 기록을 찾는다.
2. `docs/Templates/Issue_Report_Template.md`와 `docs/Troubleshooting/README.md`를 읽는다. 템플릿의 구조만 참고하고 예시 환경·날짜·수치·출처를 실제 사건의 정보로 복사하지 않는다.
3. 사용자에게 받은 환경, 실행 명령, 로그, 적용 조치, 결과를 모은다. 빠진 정보가 원인 판단에 영향을 주면 그 한계를 설명하고 꼭 필요한 질문만 묻는다. 빈 항목마다 `미제공`·`미확인`을 반복하지 않는다. 답을 기다리는 동안 확인된 부분은 정리한다.

| 정보의 성격 | 기록 방식 |
| :--- | :--- |
| 사용자 제공 로그·증상·조치 | 관측 사실과 발생 환경 |
| 공식 문서·이슈의 설명 | 적용 버전과 실제 읽은 출처 |
| 로그에서 추론한 원인 | 가설, 근거, 반증하거나 확인할 방법 |
| 아직 적용하지 않은 해결책 | 제안 또는 다음 진단 단계 |
| 측정·재현한 결과 | 실행 조건, 명령, 실제 결과 |

로그의 토큰, 개인정보, 내부 접속 정보는 공개 문서에 맞게 치환하되 오류 코드, 스택 흐름, 진단에 필요한 수치는 보존한다. 제공되지 않은 운영 성과나 사건 시각을 만들지 않는다.

## 문서 구성

문제 크기에 맞게 템플릿을 줄이거나 확장한다. 다음 정보가 서로 연결되도록 쓴다.

- 배경과 환경: 기술·버전, 실행 조건, 사용자가 하려던 작업.
- 현상과 영향: 기대 동작, 실제 동작, 핵심 로그, 확인된 영향 범위.
- 재현과 진단: 입력·명령·관찰 결과, 배제한 가설과 그 근거. 재현하지 못했다면 진단 계획으로 표시한다.
- 원인: 근거가 있는 결론과 남은 가설을 구분한다. 오류가 사라졌다는 사실만으로 근본 원인이 증명되었다고 쓰지 않는다.
- 조치: 실제 적용한 변경과 제안, 임시 우회와 근본 해결을 구분한다. 설정 변경에 영향을 받는 조건을 적는다.
- 검증: 해결을 판단할 기준과 확인 결과. 미검증이면 필요한 검증을 남긴다. 성능 개선 수치는 같은 측정 조건이 확인된 경우에만 비교한다.
- 재발 방지와 출처: 확인된 원인에 대응하는 점검 항목, 관련 TIL 문서, 공식 참고 자료.

기록 작성만으로 운영 DB, 클러스터, 버킷에 명령을 실행하지 않는다. 로컬 재현이 필요하면 격리된 임시 환경을 쓰고, 위험한 정리·삭제 명령을 무조건 복사해 실행할 수 있는 해결책처럼 제시하지 않는다.

## 저장 위치와 완료

기존 기술 문서 안의 사례라면 해당 위치를 보완한다. 독립적인 사건 기록이면 `docs/Troubleshooting/`에 작성한다. 양쪽에 같은 본문을 복제하지 않는다.

`docs/Troubleshooting/README.md`의 관련 표에 링크를 넣는다. 이 파일의 링크는 `scripts/generate_sitemap.py`가 트러블슈팅 목차를 만드는 데 사용한다. `docs/Troubleshooting/`에 파일을 추가했다면 그 폴더의 `.pages`에도 등록한다.

`til-doc-verify`로 문서와 링크를 확인하고, 원격 반영은 `git-workflow`를 따른다. 최종 결과에 문서 경로, 확인된 원인 또는 현재 가설, 적용·검증 상태를 전달한다.
