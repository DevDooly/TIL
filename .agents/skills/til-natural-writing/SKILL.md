# 자연스러운 TIL 문체 (humanize-korean 통합)

다시 같은 문제를 만났을 때 도움이 되는 개발 기록을 쓴다. 작성자의 목소리를 인위적으로 꾸미기보다, AI 특유의 번역투·상투구·기계적 문장 리듬을 걷어내고 어떤 상황에서 무엇이 일어나고 왜 그런지 자연스러운 한국어로 설명한다.

정밀한 문장 단위 AI 티 진단·교정이 필요할 때는 함께 설치된 [humanize-korean](../humanize-korean/SKILL.md)의 슬림 룰북([quick-rules.md](../humanize-korean/references/quick-rules.md))과 어휘 점검 스크립트(`.agents/skills/humanize-korean/scripts/lexical_layer.py`)를 참조한다.

## 1. 쓰기 전에 (의미 불변과 진실성)

- **사실·코드·수치·버전 100% 보존**: 사용자가 준 메모와 기존 문서의 코드, 로그, 수치, 버전 조건, 고유명사, 출처는 한 글자도 임의로 바꾸지 않는다. `API`, `LLM`, `JVM`, `prompt`, `token`, `pipeline`처럼 개발 현장에서 굳어진 표준 기술 용어는 억지로 직역(`prompt` → `지시문` ✗)하지 않고 원어를 유지한다.
- **서법과 내용 앵커 보존**: 추정·유보(`~일 수 있다`, `~로 보인다`)를 사실 단정(`~한다`)으로 과장하거나, 당위(`~해야 한다`)의 강도를 임의로 바꾸지 않는다. 문장의 핵심 개념어(내용 앵커)는 조사와 어미만 다듬고 어휘 원형을 유지한다.
- **격식(Register) 일관성**: 새 기술 문서는 담백한 평서체(`~다`)를 기본으로 하되, 사용자가 원하는 문체가 있으면 따른다. 한 문서 안에서 경어법 단계가 섞이지 않게 하고, 자연스러운 과거형(`~했다`)을 딱딱한 `~하였다`로 격상시키지 않는다.
- **경험 날조 금지**: 일반 사용법은 사용법으로, 재현 실험은 실험으로 쓴다. 근거 없는 "운영에서 겪었다", "해결했다", "성능이 크게 개선됐다" 같은 가짜 경험담을 덧붙이지 않는다.

## 2. 설명을 바로 시작하고 구조 다듬기

첫 문단에서 문제나 핵심 동작을 바로 설명한다. "본 문서는 …을 체계적으로 정리한 가이드다", "크게 세 가지로 나눌 수 있다" 같은 도입구보다 "파일을 삭제했는데 용량이 그대로라면 이전 버전이 남아 있는지 확인한다"가 독자에게 필요한 정보다.

- **문단과 리스트의 조화 (TIL 기술 문서 장르 기준)**:
  - 일반 산문·칼럼과 달리 TIL 기술 문서에서는 **절차(번호 목록), 옵션·속성 비교(표), 주의사항 콜아웃(`> [!NOTE]`)**이 가독성에 필수적이므로 유지한다. (단, 리스트 시작 전에는 반드시 빈 줄을 두어 `scripts/validate_markdown_lists.py` 규칙을 지킨다.)
  - 반대로 두세 문장으로 이어 설명하면 충분한 원리 해설까지 모두 한 줄짜리 개조식 불릿이나 콜론 부제 헤딩(`X: Y`)으로 잘게 쪼개지 않는다.
- **문장 호흡과 리듬**:
  - 길이가 똑같은 문장이나 동일한 종결어미(`~다`, `~고 있다`)만 4문장 이상 기계적으로 반복하지 않는다. 짧은 단문과 인접 문장을 자연스럽게 이은 문장을 섞어 리듬을 만든다.
  - `"A가 아니라 B다"`, `"단순한 X를 넘어 Y로"` 같은 대칭 대구 구문은 문서 전체에서 꼭 필요한 한 곳만 남기고 나머지는 직접적인 평서문으로 푼다.
- **연결어미 뒤 불필요한 쉼표 제거 (`C-11`)**:
  - `~고,`, `~며,`, `~지만,`, `~면서,`, `~아서/어서,`처럼 연결어미 직후에 기계적으로 찍힌 쉼표는 한국어 글에서 가장 강한 AI 신호 중 하나다. 문장이 너무 길어 의미가 헷갈리는 예외를 제외하고 연결어미 뒤 쉼표는 걷어내며, 문장을 다듬을 때 새 연결어미 쉼표를 넣지 않는다.
- **시각 장식 절제**:
  - 문장마다 핵심 단어를 굵게(`**`) 칠하거나 불필요한 따옴표 강조, 이모지를 남발하지 않는다.

## 3. 한국어 번역투와 AI 상투어 교정

특정 단어를 문맥 없이 기계적으로 일괄 치환하지 않고, 읽다가 걸리는 영어 직역 구문과 공허한 수식어를 자연스러운 한국어 동사·형용사로 풀어쓴다.

| 유형 | 피해야 할 AI 투 / 번역투 표현 | 자연스러운 한국어 교정 방향 |
| :--- | :--- | :--- |
| **소유·상태 직역 (`A-7`)** | `"높은 처리량을 가지고 있다"`, `"영향을 미치게 된다"` | `"처리량이 높다"`, `"영향을 준다"` |
| **이중 피동·영어식 피동 (`A-8`, `A-9`)** | `"판단되어진다"`, `"보여진다"`, `"스레드에 의해 실행된"` | `"판단된다"`, `"보인다"`, `"스레드가 실행한"` |
| **번역투 조사·후치사 (`A-2`~`A-5`, `A-19`)** | `"~에 있어서"`, `"~와 관련하여"`, `"~를 통해"` 남발, `"환경에서의"` | `"~에서"`, `"~에"`, `"~로/~해서"`, `"환경에서 나타나는"` |
| **긴 좌향 수식 (`A-18`)** | 명사 앞에 3어절 이상 긴 관형절이 붙은 문장 | 두 문장으로 나누거나 뒤로 풀어 설명 |
| **추상 명사화 체인 (`F-4`, `F-5`)** | `"정합성 확보를 수행한다"`, `"실천적 기반"`, `"-성/-적/-화"` 누적 | `"정합성을 맞춘다"`, `"실천의 기반"` (`-적`을 뗐을 때 명사 3개가 조사 없이 연달아 붙으면 풀어쓴다) |
| **분열문·형식명사 결말 (`D-8`, `I-1`~`I-3`)** | `"중요한 것은 X라는 점이다"`, `"~인 것이다"`, `"~다는 뜻이다"` | `"X가 중요하다"`, `"~다"`로 주어·서술어 직결 |
| **이중 완곡 (`G-2`)** | `"~할 가능성이 있을 수 있다"`, `"~로 보여질 수 있다"` | `"~할 수 있다"`, `"~로 보인다"` (유보 의미는 유지하되 겹침만 제거) |
| **공허한 의의·도치 결말 (`D-2`, `D-10`, `D-14`)** | `"시사하는 바가 크다"`, `"주목할 만하다"`, `"~하는 이유다"`, `"청사진/신호탄/잠식"` | 수식 문패를 지우고 구체적인 결과나 조건을 바로 서술 |
| **어색한 번역 어휘 (Lexical Layer)** | `"세 가지 렌즈로 보면"`, `"두 축"`, `"핵심 기둥"`, `"층위"`, `"짚고 간다"`, `"성공을 달성하다"` | `"세 가지 관점에서 보면"`, `"두 가지"`, `"핵심 과제"`, `"단계/수준"`, `"살펴본다"`, `"성공하다"` |

> 기존 문서에서 어색한 번역 어휘가 어디에 쓰였는지 빠르게 스캔하려면 아래 명령을 활용할 수 있다.
> ```bash
> python3 .agents/skills/humanize-korean/scripts/lexical_layer.py hints --input <문서경로> --genre report
> ```

## 4. 독자에게 필요한 주의점만 남기기

"기존 설명은 잘못됐다", "일반화해서는 안 된다", "성과로 해석하지 않는다" 같은 편집·검토 지시는 본문에 남기지 않는다. 실제 동작과 적용 조건으로 바꾼다. 정정 내역 자체가 필요한 요청이라면 무엇을 정정했는지 별도로 설명한다.

검증하지 않은 부분을 숨기지는 않는다. "아래 코드는 실행기 포화만 테스트한다. DB 트랜잭션은 서비스 통합 테스트로 확인해야 한다"처럼 한계를 해당 예제 옆에서 구체적으로 설명한다. 같은 면책 문구를 서론·본문·결론에 반복하지 않는다.

파괴적인 명령의 범위, 데이터 손실 가능성, 버전별 차이 같은 중요한 조건은 문체를 다듬는 과정에서도 남긴다. 원인을 확정할 근거가 없으면 추정임을 밝히고, 성공 결과가 없으면 검증 계획으로 쓴다.

## 5. 날짜와 작성 흔적

- 문서마다 작성일·수정일·확인일을 자동으로 붙이지 않는다. 편집 날짜는 Git 이력과 자동 변경 로그에서 관리한다.
- 장애 타임라인, 배포 순서, 종료 예정일, 시점에 따라 달라지는 지원 정책처럼 독자의 판단에 필요한 날짜는 관련 설명 안에 남긴다. 실제 사건 날짜나 코드·로그 속 날짜를 일괄 삭제하지 않는다.
- 적용 버전은 날짜와 다르다. "이 예제는 JDK 21 API를 사용한다"처럼 재현에 필요한 버전은 유지한다. 확인일만 오늘로 바꿔 검증한 것처럼 보이게 하지 않는다.
- 작성자 필드, 빈 템플릿 항목, "확인 필요" 목록은 관례적으로 만들지 않는다. 빠진 정보가 판단을 바꾼다면 그 부분만 문장으로 설명한다.
- TIL 문서를 직접 작성·수정할 때는 `_workspace/` 임시 폴더나 `<!-- HUMANIZE-SUMMARY -->` 주석 블록을 문서 안에 남기지 않는다. (사용자가 별도 원고에 대해 `/humanize-korean` 정밀 파이프라인 실행을 명시적으로 요청한 경우에만 `humanize-korean` 스킬 절차를 따른다.)

## 6. 표현을 고치는 예

**수정 전**

> 본 문서는 JDK 21 환경에서의 스레드 풀 설정에 대해 체계적으로 짚고 간다. 기준: JDK 21, 확인일: YYYY-MM-DD. newFixedThreadPool에 AbortPolicy를 적용하는 것을 통해 요청이 즉시 거절되어진다고 설명하는 것은 잘못된 안내라는 점에 주목할 필요가 있다.

**수정 후**

> 아래 예제는 JDK 21 API를 사용한다. `newFixedThreadPool`은 스레드 수만 제한하므로 DB가 느려지면 요청이 대기 큐에 계속 쌓인다. 큐가 가득 찼을 때 추가 요청을 바로 거절하려면 큐 크기도 함께 제한해야 한다.

**수정 전**

> 결론적으로, 이는 데이터 파이프라인 설계의 두 축에 있어서 시사하는 바가 크다. 결과 및 제언: 검증되지 않은 개선율을 운영 성과로 서술하지 않는다.

**수정 후**

> 같은 입력으로 변경 전후의 처리 시간과 오류율을 비교한다. 아직 측정 결과가 없다면 다음에 확인할 항목으로 남긴다.
