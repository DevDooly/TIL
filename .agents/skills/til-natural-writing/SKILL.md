# 자연스러운 TIL 문체

다시 같은 문제를 만났을 때 도움이 되는 개발 기록을 쓴다. 작성자의 목소리를 꾸미기보다, 어떤 상황에서 무엇이 일어나고 왜 그런지 읽기 쉽게 설명한다.

## 쓰기 전에

- 사용자가 준 메모와 기존 문서에서 증상, 원인, 적용한 변경, 실제 결과를 구분한다. 기존 문서를 다듬을 때는 코드·로그·수치·버전 조건·출처를 먼저 파악한다.
- 새 문서는 담백한 평서체를 기본으로 한다. 사용자가 원하는 문체가 있으면 따른다. 존댓말을 반말로 바꾸는 것만으로 자연스러워졌다고 판단하지 않는다.
- 일반 사용법은 사용법으로, 재현 실험은 실험으로 쓴다. 근거 없는 "운영에서 겪었다", "해결했다", "크게 개선됐다" 같은 경험을 덧붙이지 않는다.

## 설명을 바로 시작하기

첫 문단에서 문제나 핵심 동작을 설명한다. "본 문서는 …을 체계적으로 정리한 가이드다" 같은 소개보다 "파일을 삭제했는데 용량이 그대로라면 이전 버전이 남아 있는지 확인한다"가 독자에게 필요한 정보다.

문장은 구체적인 대상과 동작을 중심으로 쓴다. "정합성 확보를 수행한다"보다 무엇을 비교하고 어떤 결과여야 하는지 적는다. 조건과 예외는 관련 설명 옆에 두어 왜 필요한지 알 수 있게 한다.

- 관련된 문장은 짧은 문단으로 연결한다. 모든 문장을 한 줄짜리 불릿으로 쪼개거나, 길이가 같은 문장만 이어 쓰지 않는다.
- 순서가 있는 작업에는 번호 목록을, 조건 비교에는 표를 쓴다. 설명 두세 문장이면 충분한 내용까지 표나 체크리스트로 만들지 않는다.
- 제목은 "삭제했는데 용량이 줄지 않는 이유"처럼 내용을 드러내게 쓴다. 모든 문서에 배경·분석·해결·결론·교훈을 같은 순서로 강제하지 않는다.
- 이모지, 과도한 굵게 표시, 한영 병기, "완벽한", "혁신적인", "반드시", "핵심" 같은 강조는 필요할 때만 쓴다. 특정 단어를 기계적으로 금지하거나 치환하지 않는다.
- API·설정명은 그대로 두고, 설명에서는 익숙한 한국어를 쓴다. 의미가 분명한 "대기 큐 상한"을 굳이 "bounded queue 상한 범위"처럼 늘이지 않는다.

## 독자에게 필요한 주의점만 남기기

"기존 설명은 잘못됐다", "일반화해서는 안 된다", "성과로 해석하지 않는다" 같은 편집·검토 지시는 본문에 남기지 않는다. 실제 동작과 적용 조건으로 바꾼다. 정정 내역 자체가 필요한 요청이라면 무엇을 정정했는지 별도로 설명한다.

검증하지 않은 부분을 숨기지는 않는다. "아래 코드는 실행기 포화만 테스트한다. DB 트랜잭션은 서비스 통합 테스트로 확인해야 한다"처럼 한계를 해당 예제 옆에서 구체적으로 설명한다. 같은 면책 문구를 서론·본문·결론에 반복하지 않는다.

파괴적인 명령의 범위, 데이터 손실 가능성, 버전별 차이 같은 중요한 조건은 문체를 다듬는 과정에서도 남긴다. 원인을 확정할 근거가 없으면 추정임을 밝히고, 성공 결과가 없으면 검증 계획으로 쓴다.

## 날짜와 작성 흔적

- 문서마다 작성일·수정일·확인일을 자동으로 붙이지 않는다. 편집 날짜는 Git 이력과 자동 변경 로그에서 관리한다.
- 장애 타임라인, 배포 순서, 종료 예정일, 시점에 따라 달라지는 지원 정책처럼 독자의 판단에 필요한 날짜는 관련 설명 안에 남긴다. 실제 사건 날짜나 코드·로그 속 날짜를 일괄 삭제하지 않는다.
- 적용 버전은 날짜와 다르다. "이 예제는 JDK 21 API를 사용한다"처럼 재현에 필요한 버전은 유지한다. 확인일만 오늘로 바꿔 검증한 것처럼 보이게 하지 않는다.
- 작성자 필드, 빈 템플릿 항목, "확인 필요" 목록은 관례적으로 만들지 않는다. 빠진 정보가 판단을 바꾼다면 그 부분만 문장으로 설명한다.

## 표현을 고치는 예

**수정 전**

> 기준: JDK 21, 확인일: YYYY-MM-DD. newFixedThreadPool에 AbortPolicy를 설명하며 요청이 즉시 거절된다고 하면 잘못된 안내다.

**수정 후**

> 아래 예제는 JDK 21 API를 사용한다. `newFixedThreadPool`은 스레드 수만 제한하므로 DB가 느려지면 요청이 큐에 계속 쌓일 수 있다. 추가 요청을 거절하려면 큐 크기도 제한해야 한다.

**수정 전**

> 결과 및 제언: 검증되지 않은 개선율을 운영 성과로 서술하지 않는다.

**수정 후**

> 같은 입력으로 변경 전후의 처리 시간과 오류율을 비교한다. 아직 측정 결과가 없다면 다음에 확인할 항목으로 남긴다.

## 마지막으로 읽어보기

도입부만 읽어도 무엇을 다루는지 알 수 있는지, 주의문이 설명을 가로막지 않는지, 끝의 요약이 앞 내용을 반복하는지 살핀다. 어색한 연결과 불필요한 문장만 덜어내고 설명에 필요한 깊이는 유지한다.

기존 글을 고쳤다면 원문과 비교해 사실·조건·코드·출처가 달라지지 않았는지 확인한다. 기술 내용을 고쳐야 할 이유가 발견되면 그 변경은 따로 근거를 확인한다. 문체를 다듬은 작업을 기술 검증이나 실제 운영 재현을 마친 것처럼 보고하지 않는다.
